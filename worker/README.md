## Cloudflare setup (Claude, after Sean authorizes publishing)

From this directory, use a recent Node and Wrangler. First run the relevant `--help` commands. Wrangler was unavailable in the build environment; the setup commands below follow Cloudflare's [D1 guide](https://developers.cloudflare.com/d1/get-started/) and [KV guide](https://developers.cloudflare.com/kv/get-started/).

Use the scoped credentials in `/Users/seanmacebo/Workspace/data-pipelines/credentials/cloudflare_nest.json` (`api_token`, `account_id`). For setup commands, load those values into your process environment without printing them, or use your already authenticated Wrangler login. `deploy.sh` reads the JSON directly and passes credentials only through the subprocess environment.

```sh
cd /Users/seanmacebo/Workspace/projects/nest/worker
npx --yes wrangler --help
npx --yes wrangler d1 --help
npx --yes wrangler kv namespace --help
npx --yes wrangler secret --help
npx --yes wrangler d1 create nest
npx --yes wrangler kv namespace create FILES
# Replace REPLACE_D1_ID and REPLACE_KV_ID in wrangler.toml with those results.
npx --yes wrangler d1 execute nest --remote --file=./schema.sql
```

Generate each password hash with `node tools/hash_password.mjs` (password on stdin, then EOF; use hidden input in your terminal). It prints only a salted PBKDF2-SHA256 hash with 100,000 iterations. Set these secrets via Wrangler's prompts:

```sh
npx --yes wrangler secret put USERS_JSON
# One JSON object: {"sean":"pbkdf2$100000$...$...","mishka":"pbkdf2$100000$...$..."}
npx --yes wrangler secret put SESSION_SECRET
npx --yes wrangler secret put WORKER_TOKEN
```

Use independently generated random values (at least 32 bytes) for the last two. Changing SESSION_SECRET invalidates all sessions; removing a name from USERS_JSON disables that account. Sessions otherwise last 90 days. `run_worker_first = true` protects every private asset, including direct HTML and image URLs; see [asset binding behavior](https://developers.cloudflare.com/workers/static-assets/binding/).

Only after setup and publishing approval:

```sh
./deploy.sh
```

That script builds and runs `npx --yes wrangler deploy` with credentials from the JSON. Do not commit credentials, password hashes, `.dev.vars`, or inbox files to either repository. This build task did not change git configuration, stage, commit, push, or disable GitHub Pages.

## Mac inbox setup

Create `~/babybean/nest_inbox.json`, mode 600:

```json
{"base_url":"https://nest.YOUR-SUBDOMAIN.workers.dev","worker_token":"SAME_WORKER_TOKEN_SECRET"}
```

`nest_inbox.py` reuses `~/babybean/config.json` for `claude_bin`, permission mode, extra directories, disallowed tools, extra environment, and the OAuth token path. It never resumes Telegram sessions. Attachments live in `~/babybean/nest_inbox/<request-id>/`. A file lock prevents overlap. The runner includes its `lease_until` in replies so a stale process cannot overwrite a reclaimed job. Claude gets a 40-minute hard timeout; the Worker leases jobs for 45 minutes. Heartbeats continue while Claude runs. Files can lag the queue briefly because KV is eventually consistent, so downloads retry. Replies awaiting acknowledgement survive in `nest_inbox_pending.json`; expired claims are archived as `undelivered.json` rather than overwriting a newer answer.

Check that `/opt/homebrew/bin/python3` has `requests` installed, and adjust the interpreter in `~/babybean/com.babybean.nestinbox.plist` if needed. Once live testing is authorized, run the poller manually, verify a question with an attachment and reply, then copy the template to `~/Library/LaunchAgents/` and load it with `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.babybean.nestinbox.plist`. It runs every 60 seconds; both streams log to `~/babybean/nest_inbox.log`. The template has not been installed or loaded.

Requests to change the Nest authorize Babybean to build and deploy those future changes. The inbox runner itself does not deploy anything; its Claude system prompt explains that workflow. Telegram notifications use the existing `telegram_notify.notify` wrapper after the reply is saved.

## Migration and checks

Local storage is per origin: phones on GitHub Pages cannot automatically supply data to workers.dev. Before switching either phone, export its `nest_*` localStorage values privately, then import them on the new origin after login. Do not import `nest_sync_*` internal keys. The first API sync retains a private `nest_sync_migration_backup` on the phone, uploads missing keys, unions old ticks/saves, and uses cloud values for other existing keys. Later writes use revisions, persist an outbox, and merge only changed fields/list records on conflict, preserving removals. Export both phones before cutting over. Existing public Pages copies stay public until separately retired.

```sh
./build.sh
node tests/worker.mjs
node tests/client.mjs
python3 tests/poller.py
```

Node 22.13+ is needed for the tests' built-in SQLite adapter. These are offline tests of SQL/auth/API behavior, two-phone syncing, and the Mac runner with mocked Claude/network calls. Browser validation could not run because the sandbox blocked localhost binding and Chrome launch. These checks are not a substitute for phone/browser and Cloudflare runtime smoke tests. After setup, also verify: anonymous private assets/API denied, phone login/logout and install icons, cross-phone pacer/to-do/milestone edits, offline retry, and a real attachment question/reply. No live API or Claude invocation was made by the test suite.

Files are limited to five, 20 MiB each. Cloudflare's aggregate request-body limit can prevent sending five maximum-size files in one form; send a smaller batch in that case. Attachments download as attachments with nosniff rather than executing uploaded HTML. Passwords, machine credentials, and session keys are never shipped in generated assets.
